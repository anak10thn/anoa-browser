## 2026-04-23 — task-004: Phase 3 HTTP Discovery Server

- QTcpServer::newConnection slot may block the event loop if we use waitForReadyRead() + a nested QEventLoop for upstream requests; acceptable for a single-client CDP discovery server but would need async redesign for high-concurrency use.
- QNetworkAccessManager created on the stack inside a slot with a nested QEventLoop works correctly in Qt — the inner loop pumps events (including the NAM reply) without interfering with the outer app.exec() loop.
- Host header rewriting: strip the port suffix from the Host header (detect it by parsing the last ':' segment as a uint16) to get the bare hostname, then replace 127.0.0.1 in the upstream response body. This preserves the Chromium debug port in webSocketDebuggerUrl while making it reachable from remote hosts.
- debuggingPort convention: the HttpServer receives port+1 as the Chromium DevTools port. Chromium starts its DevTools HTTP listener on the port passed via --remote-debugging-port (set in QTWEBENGINE_CHROMIUM_FLAGS), which must differ from the port HttpServer binds to.
- cmake not installed on dev machine; live build validation skipped again — CI must verify.
- `static` free function `sendResponse()` in the .cpp file avoids repetition of the HTTP framing for all response paths (200, 401, 404, 503).

## 2026-04-23 — task-005: Phase 4 CDP WebSocket Proxy

- `QWebSocketServer::nextPendingConnection()` returns a parentless socket; caller owns it and must call `deleteLater()` when done.
- `QWebSocket::request()` returns a `QNetworkRequest` — use `rawHeader("Authorization")` to read the Bearer token header. Works only after the WebSocket handshake completes (i.e., inside `newConnection` slot).
- `QWebSocket::requestUrl()` returns the full URL including query params; wrap with `QUrlQuery(socket->requestUrl())` to extract `?token=`.
- Per-session isolation: use two maps (`clientToUpstream` + `upstreamToClient`) so each disconnect handler can find its paired socket via `qobject_cast<QWebSocket*>(sender())`.
- Upstream socket created with `new QWebSocket(QString(), QWebSocketProtocol::VersionLatest, this)` — parenting to `this` means it's auto-deleted on CdpProxy destruction as a safety net; `deleteLater()` is still called explicitly on clean disconnect.
- PORT CONFLICT: both `HttpServer` and `CdpProxy` are instantiated with `config.port` as their listen port. `QTcpServer` and `QWebSocketServer` cannot share a port — the second `start()` will log a warning and return false. This is a design issue to be resolved in a future task (likely by combining them into a single multiplexed listener or placing CdpProxy on a separate port with URL rewriting).

## 2026-04-23 — task-007: Phase 6 Extension and Profile Management

- Constructor refactored to always start with QWebEngineProfile::defaultProfile(); setupNamedProfile() is the single place where named profiles are created with ForcePersistentCookies. This avoids double-creation when both constructor and main.cpp would otherwise set up profiles.
- main.cpp must call setupNamedProfile BEFORE loadExtensions so content-script QWebEngineScripts are inserted into the correct (named) profile's script collection. Inserting into defaultProfile then replacing it loses the scripts.
- getCookies() uses QWebEngineCookieStore::loadAllCookies() + cookieAdded signal + QEventLoop + QTimer::singleShot(500ms) to bridge the async cookie store to a synchronous return. Qt provides no "done loading" signal; a 500ms window is sufficient for local cookie stores.
- Replacing the page after setupNamedProfile: QWebEngineView::setPage() does NOT delete the old page automatically ("This may be changed in future releases" per Qt docs) — always call oldPage->deleteLater() explicitly after setPage().
- QWebEngineProfile::clearAllVisitedLinks() silently fails on the default profile — only works on named profiles; no error is thrown, making it safe to call unconditionally.
- For clearStorage, use page()->triggerAction(QWebEnginePage::Stop) rather than page()->action(...)->trigger() — triggerAction is the correct one-call API for executing a web action.
- Manifest v3 extension loading: log qWarning and skip silently; Qt6 WebEngine's QWebEngineProfile has no manifest v3 support as of Qt 6.4–6.6; content script injection via QWebEngineScript works only for manifest v1/v2.
- cmake not installed on dev machine; live build validation skipped again — CI must verify.

## 2026-04-23 — task-010: Phase 10 Integration Validation

### Build

- `#include <QJsonArray>` must be explicit in config.cpp (forward declarations in qmetatype.h are insufficient for `toArray()` in Qt 6.10).

- `-s` linker flag is GNU ld only; must guard with `if(UNIX AND NOT APPLE)` in CMakeLists.txt or macOS build fails at link time.

### Architecture Bug Fixes Found During Validation
- **Critical**: `AnoaBrowser` was setting `--remote-debugging-port=config.port` (e.g. 9222) but `HttpServer` was designed to proxy from `config.port` to `config.port+1`. Fixed: AnoaBrowser now uses `config.port + 1` for Chromium's DevTools, so the port layout is: HTTP=9222, Chromium=9223, CdpProxy=9224.
- **Critical**: `HttpServer` and `CdpProxy` both tried to listen on the same `config.port`. Fixed by using port+2 for CdpProxy and adding `proxyPort` parameter to `HttpServer` so it rewrites `webSocketDebuggerUrl` from port+1 to port+2.
- **Critical**: `HttpServer` URL rewriting only replaced `127.0.0.1` (hostname) but not the port number. The rewrite must replace `127.0.0.1:<debugPort>` → `hostname:<proxyPort>` first, then bare `127.0.0.1` remaining.
- **Critical**: Playwright requests `/json/version/` (trailing slash). HttpServer must normalize trailing slashes before path matching.
- **Critical**: `CdpExtensions::processCommand` was called with `nullptr` as the page pointer in `CdpProxy::onClientMessage`. For `Page.printToPDF` this caused a null pointer dereference (crash). Fixed: CdpProxy now stores `m_page` (set via `setPage()`) and passes it to processCommand.
- **Page visibility**: `QWebEnginePage` does not appear in `/json/list` until it navigates. Added `load(QUrl("about:blank"))` in `AnoaBrowser::init()` to activate the renderer process.

### CDP Protocol Gap Summary (Qt 6.10.2, Chrome 134)
- `Target.createTarget` → NOT SUPPORTED (error -32000). Cannot create new tabs/pages via CDP. Workaround: use the page created at startup.
- `Target.createBrowserContext` → NOT SUPPORTED (error -32000). Proxy now stubs it with synthetic ID `__anoa_default__` and strips the ID from `Target.createTarget` before forwarding (via `CdpExtensions::rewritePassthrough`).
- `Browser.setDownloadBehavior` and other Browser context management commands → NOT SUPPORTED. Proxy stubs them with `{}`.
- `Page.printToPDF` → not in Chromium DevTools for this build (error -32601). Handled by Qt's `QWebEnginePage::printToPdf` via PdfHandler; proxy must be initialized with `setPage()`.
- `Profiler.*`, `HeapProfiler.*`, `Security.*` → all stubbed to `{}` (no Qt API equivalents).

## 2026-04-24 — task-011: Phase 1 Config Extension (width/height)

- `QCommandLineOption widthOpt({"width"}, ...)` uses an initializer-list constructor — single-char shortcuts not added here since "w" and "h" are not reserved by existing options, but were omitted to keep the interface explicit.
- `QString::toInt(&ok)` is the correct pattern for validated integer conversion from CLI strings; always check the `ok` bool and validate the semantic range (> 0) separately from the parse success.
- File-first, CLI-override pattern: load config file into `cfg` first, then overwrite only fields where `parser.isSet()` is true — same pattern as existing port/headless fields.
- JSON: use `obj["width"].toInt(1280)` with a fallback default, guarded by `obj.contains("width")` — avoids silently resetting to 0 when the key is absent.
- INI: `ini.value("width", 1280).toInt()` with a QVariant default is the correct pattern matching existing port/headless INI reads.

## 2026-04-24 — task-012: Phase 2 Browser Core Wiring (width/height)

- `resize(m_config.width, m_config.height)` must be called BEFORE `load(QUrl("about:blank"))` in `AnoaBrowser::init()` — the initial render (and all subsequent CDP `Page.captureScreenshot` calls) uses whichever surface size was set at load time.
- The resize call is unconditional: `QWebEngineView::resize()` resizes the visible QWidget window in headed mode and sets the off-screen surface size in headless/offscreen mode — one call covers both.

## 2026-04-24 — task-013: Phase 3 Validation (resolution flags end-to-end)

### Bugs Found and Fixed During Validation

1. **Build blocker** (`src/config/config.cpp`): `QCommandLineOption({"width"}, ...)` is ambiguous on macOS Qt 6.10. Fixed to `QCommandLineOption(QStringList{"width"}, ...)`.

2. **Headless viewport 0×0** (`src/browser/anoa_browser.cpp`): `QWebEngineView::resize()` has no effect unless `show()` is called first. With `QPA_PLATFORM=offscreen`, `show()` creates an invisible backing surface — the view has no surface otherwise and reports 0×0 viewport. Fixed by calling `show()` unconditionally in `init()` (removing the `if (!m_config.headless)` guard).

3. **Headless screenshot crash** (`src/browser/anoa_browser.cpp`): Without `--disable-gpu`, Chromium's Skia rasterizer fails with "Unable to initialize SkSurface" on hosts without GPU and `Page.captureScreenshot` crashes the process. Fixed by auto-appending `--disable-gpu` to `QTWEBENGINE_CHROMIUM_FLAGS` when `m_config.headless` is true.

4. **CdpProxy upstream handshake race** (`src/cdp/cdp_proxy.cpp`, `src/cdp/cdp_proxy.h`): When a client connects and immediately sends a CDP command, the upstream WS connection to Chromium may not be established yet. `QWebSocket::sendTextMessage` on a non-connected socket silently drops the message. Fixed by: queuing client messages in `m_pendingMessages[upstream]` when `upstream->state() != ConnectedState`, and flushing the queue in a new `onUpstreamConnected()` slot.

### Patterns Discovered

- macOS QtWebEngine headless: `show()` is required even for offscreen mode — without it the Skia surface is never created and the viewport is 0×0.
- Headless screenshot via CDP requires `--disable-gpu` on machines without a GPU (the default on CI/dev Mac headless).
- CdpProxy upstream connection is asynchronous; any CDP client that sends immediately on WS open risks the race. The message queue fix is critical for reliable operation.
- Validation scripts that launch multiple browser instances sequentially must kill the entire process group (Chromium spawns renderer/GPU sub-processes that outlive the main process on SIGTERM). Use `process.kill(-proc.pid)` after `detached: true`, or ensure long enough gap between instances.
